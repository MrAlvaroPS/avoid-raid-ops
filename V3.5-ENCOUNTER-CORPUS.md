# Encounter Intelligence Corpus — design and operating notes

## Goal

Avoid maintaining one large hand-written ruleset for every boss, difficulty and season. AvoiD Raid Ops should learn the reusable encounter structure from Warcraft Logs and only require human intervention for ambiguous mechanics.

## Corpus key

A corpus is scoped by:

`encounterId / difficulty / partition`

Partition `0` means "current WCL default". The resolved default partition ID is recorded. If it changes during enrichment, the job pauses rather than combining two ranking partitions silently.

## Wide corpus

The wide layer starts from `Encounter.fightRankings` and discovers public ranked kill reports. For every unique report, it keeps all fights for the requested encounter/difficulty and summarizes WCL tables separately for kills and wipes:

- enemy casts;
- friendly damage taken;
- debuffs;
- buffs;
- interrupts;
- deaths.

Only compact normalized profiles are persisted, not giant raw table responses.

This allows thousands of reports to establish population-level signals such as:

- ability prevalence in kills vs wipes;
- events per pull;
- whether a signal is normal on successful kills;
- whether a signal is enriched in wipes.

## Deep sample

A deterministic subset is then fetched with event data:

- enemy casts;
- friendly damage taken;
- interrupts;
- buffs/debuffs;
- deaths.

It is used for temporal and state inference:

- begin-cast vs completed cast;
- interrupt rates;
- approximate damage occurrence fan-out;
- events near phase transitions;
- short-window death association;
- mutually exclusive player-state dimensions;
- state-to-mechanic matching/mismatching.

If an event stream hits WCL's page limit in the current profiler, that stream is marked incomplete and **does not contribute its dependent inference metrics**. The model prefers missing evidence over false precision.

## Train / holdout

Report codes are hashed into a deterministic 80/20 split. Rules are inferred from the training split and independently scored on holdout data.

Current generic signatures:

1. `interrupt` — high clean-kill interrupt rate, low clean-kill completion rate.
2. `phase-transition` — normal on kills and strongly associated with phase boundaries.
3. `raid-damage` — highly prevalent in kills with broad raid fan-out.
4. `dangerous-cast` — rare on kills but enriched in wipes.
5. `avoidable-damage` — damage exposure enriched in wipes; only scoreable with a defensible occurrence denominator.
6. `wrong-state-impact` — event-backed mutually exclusive state plus strong correct-state behavior in kills.

## Publication

Compilation and publication are separate.

A candidate can be inspected early, but production runtime only loads `status: published`. Default minimum gates are deliberately large:

- 1,500 wide reports;
- 200 deep reports;
- 250 holdout reports;
- >=66% mean holdout score;
- at least one accepted mechanic.

The normal 2,500-report build therefore exceeds the minimum publication population when WCL has enough public data.

## Persistence and enrichment

Store: `avoid-raid-ops-encounter-corpus-v1` (Netlify Blobs, strong consistency).

Persisted objects include:

- resumable job state;
- compact aggregate;
- generated model;
- one wide profile per report;
- one deep profile per sampled report.

`ENRICH +500` re-scans current rankings to discover new report codes, but skips every already-processed report profile. Existing observations are reused; the whole corpus is not downloaded again.

Netlify Blobs is site-wide, so corpus data survives normal redeploys of the same Netlify site. Moving to another Netlify site requires explicit migration/export later.

## API

Status:

`GET /api/wcl/corpus?encounter=3182&difficulty=5&partition=0`

Generated model:

`GET /api/wcl/corpus?encounter=3182&difficulty=5&partition=0&action=model`

The UI drives small POST steps (`start`, `step`, `pause`, `resume`, `enrich`) instead of one long serverless invocation. This avoids Netlify Function timeout while keeping every step resumable.

## Important limits in v3.5

- The generic compiler is the foundation, not the final universal WoW encounter ontology.
- Some unusual mechanics will remain `candidate`/unclassified until more generic signatures are added.
- The deep event query currently records truncation rather than paginating every corpus report indefinitely; incomplete streams are excluded from dependent inference.
- No automatic rule is allowed to become runtime truth without holdout validation and publication gates.
- Existing manual Belo'ren knowledge is retained as a fallback and as an oracle for evaluating what the compiler rediscovers; it is no longer the intended scaling mechanism.

## v3.5.1 execution correction

The live v3.5.0 Belo'ren run proved that the scalable design needed four concrete execution changes before a large corpus could be trusted:

1. **Exact fight IDs first.** Every Wide/Deep report profile now begins with `report.fights(encounterID,difficulty)` and only then requests tables/events with the returned `fightIDs`.
2. **Partition before storage.** The active WCL partition is resolved before the corpus key is persisted; a request using partition 0 is mapped through a persistent alias to the resolved partition.
3. **Ranking as discovery seed.** Ranked reports identify guild/personal sources. The corpus itself is expanded from those sources' public reports in the raid zone and current-partition time window.
4. **Pull and diversity gates.** Corpus targets and publication gates are based on retained encounter pulls plus independent-source/report/holdout requirements, not on ranked report count alone.

Hosted corpus persistence is now strict: Netlify Blobs is required and no silent local filesystem fallback is permitted. Three consecutive identical structural pipeline errors trigger an automatic pause to protect the WCL hourly budget.

See `V3.5.1-CHANGES.md` and `V3.5.1-VERIFICATION.md` for the exact behavior and live test checklist.
