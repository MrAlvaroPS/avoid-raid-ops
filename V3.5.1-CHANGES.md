# AvoiD Raid Ops v3.5.1 — Corpus Builder structural fix

v3.5.1 replaces the first corpus-builder execution path after the v3.5.0 Belo'ren test exposed structural WCL/API and persistence problems. The release keeps the existing visual system and the full source project; the changes are concentrated in the encounter-corpus pipeline and its Mechanics workbench.

## Why v3.5.1 exists

The v3.5.0 run discovered 146 ranked seed reports but retained zero reports because WCL table queries were issued without an explicit fight range. WCL returned:

`You must either provide fightIDs, or provide startTime and endTime, or both.`

The same run also exposed two architectural problems: persistence had been keyed as partition `p0` before WCL resolved the active partition to `p4`, and the UI treated the ranked-report list itself as the intended large corpus.

## 1. Exact-fight WCL profiling

Wide and Deep profiling are now two-stage operations:

1. Fetch `report.fights(encounterID, difficulty)`.
2. Extract the matching fight IDs.
3. Query report tables/events with those exact `fightIDs`.

No corpus table/event query is allowed to rely on encounter/difficulty alone.

Wide data uses exact kill/wipe fight ID sets. Deep event streams use the exact set of matching encounter fight IDs. Reports without a matching encounter/difficulty fight are filtered normally and are not counted as pipeline errors.

## 2. Partition is resolved before persistence

A new corpus is not assigned a storage key until the first WCL ranking request resolves the active partition.

For Belo'ren Mythic on the current default partition this should create:

`3182/d5/p4`

The previous v3.5.0 `3182/d5/p0` job is intentionally not reused. A lightweight alias maps requests made with `partition=0` to the currently resolved corpus partition.

If WCL changes the default partition later, enrichment refuses to mix the new partition into the existing corpus.

## 3. Ranked reports are seeds, not the corpus

The large-sample discovery path is now:

`ranked report -> report guild / personal uploader -> public report history for the raid zone -> exact encounter fights`

The ranking list is therefore only used to identify independent sources. Each seed report is resolved to either:

- its guild, or
- the personal-log uploader when no guild owns the report.

The builder then pages public reports for those sources, scoped to the encounter raid zone and a current-partition time window. Candidate report codes are deduplicated before Wide profiling.

## 4. Pull-first targets

The workbench now targets retained encounter pulls instead of ranked report count.

Default targets:

- Wide: 2,500 pulls
- Deep: 300 pulls
- selectable Wide targets: 2,500 / 5,000 / 10,000 pulls
- Deep target scales with Wide target, capped at 1,000 pulls in the current UI

The status payload exposes both report counts and pull counts. This prevents a corpus with many reports but too few encounter pulls from being treated as sufficient.

## 5. Source diversity becomes a publication gate

The generated model tracks independent report sources and will not auto-publish solely because the raw pull count is large.

Current publication gates include:

- 2,500+ Wide pulls
- 300+ Deep pulls
- 250+ Wide reports
- 50+ Deep reports
- 50+ independent guild/personal sources
- 50+ validation/holdout reports
- at least one accepted inferred mechanic
- mean holdout validation >= 0.66

A model may compile as `candidate` when some gates are not yet satisfied.

## 6. Stratified Deep sample

Wide profiles are bucketed as:

- kill
- deep wipe
- mid wipe
- early wipe

Deep sampling rotates through these groups instead of simply taking the first N reports. Truncated event streams remain excluded from the metrics that require complete streams.

## 7. Persistent storage is mandatory on hosted Netlify

The corpus store uses `@netlify/blobs` with strong consistency.

In a hosted runtime there is no silent filesystem fallback. If the Blobs store cannot initialize, corpus work fails immediately with a persistent-storage error instead of spending WCL points on a job whose checkpoints may disappear.

Local filesystem storage remains available only for local development.

## 8. Structural-error circuit breaker

Repeated identical pipeline/API failures no longer burn through the WCL hourly budget indefinitely.

After three consecutive failures with the same normalized structural error signature, the job auto-pauses with:

- `status: "paused"`
- `pauseReason: "systemic-error"`

The user must explicitly resume after the underlying problem has been fixed.

## 9. Preflight storage health endpoint

Before starting a long corpus build, the endpoint:

`/api/wcl/corpus?encounter=<id>&action=health`

returns the corpus engine version and actual storage backend. This makes Netlify Blobs readiness testable without spending WCL API points.

## 10. Rate-limit protection remains active

The corpus continues to checkpoint every step and stops before exhausting WCL's hourly allowance. A rate-limited job retains its current phase, candidates, profiles and aggregate state and can continue after the reset window.

## 11. Current-partition history window

WCL's public `Partition` object does not expose partition start/end timestamps. v3.5.1 therefore derives a conservative history start from the earliest current-partition ranked seed report and subtracts two days before expanding source histories.

This is intentionally visible as `partitionWindowStart` in corpus status. It is a partition-isolation heuristic, not an asserted WCL partition boundary.

## 12. Full source remains the release artifact

The v3.5.1 ZIP contains the complete maintainable project, not only the currently published frontend assets:

- `apps/web/`
- `server/`
- `packages/`
- `netlify/functions/`
- `tests/`
- scripts and architecture documentation
- immutable Golden Master
- `deploy-preview/` compatibility deployment

This project can be committed to Git and connected to Netlify without relying on future manual ZIP deploys.
