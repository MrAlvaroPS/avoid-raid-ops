# v3.7 Encounter Discovery Engine

## Problem being solved

AvoiD cannot scale by manually coding every mechanic for every raid boss, difficulty, patch and season. WCL provides enough repeated encounter evidence to learn a large part of the encounter model automatically, but simple frequency mining is insufficient: a frequent ability can be normal raid damage, a phase transition, an assignment mechanic, or a failure signal.

v3.7 therefore learns relationships between signals rather than treating ability IDs independently.

## Discovery layers

### 1. Variant families

Ability names are normalized and grouped into mirrored/opposite families such as Light/Void, Fire/Frost, Solar/Lunar, Red/Blue and similar state pairs. The algorithm is generic; encounter-specific IDs are not embedded in the discovery engine.

### 2. State dimensions

Persistent, mutually-exclusive aura families can become state dimensions. Evidence includes application volume, exclusivity, balance, report/player/fight support, and mirrored-family behavior.

A state dimension can then explain why a Light-labelled mechanic and Void-labelled mechanic require different recipients without hardcoding the boss.

### 3. Stateful mechanic relationships

When a mechanic belongs to a discovered state family, the compiler checks per-target state alignment when available. If alignment is not yet strong enough, the mechanic remains observational and player blame is disabled.

### 4. Cast → enemy aura relationships

Deep profiles now capture enemy buffs/debuffs. The relation graph measures whether an enemy aura appears shortly after one or more upstream casts and whether that relation is enriched in wipes versus kills. Strong holdout-stable relationships can become a generic `failure-aura-is-failure` rule.

### 5. Kill/wipe contrast

The compiler compares prevalence and completion behavior in kills and wipes. A cast being common is not enough to call it a failure. Scoreable rules require stronger causal evidence than observational rules.

### 6. Source-isolated holdout

Train/holdout is assigned by guild/uploader source. Multiple reports from the same raid group cannot appear on both sides of validation.

## Boss Learned %

`learning.scorePct` is an evidence-weighted maturity score. It answers:

> How ready is the learned encounter model to guide Raid Ops safely?

It is composed from:

- `dataDepthPct`
- `holdoutPct`
- `signalCoveragePct`
- `semanticResolutionPct`
- `diversityPct`

The score is capped when important unresolved signals remain, a state model is unresolved, or Deep evidence is thin. This makes the number useful for deciding whether more data is likely to help.

Examples:

- low DATA, healthy SEMANTICS → collect more Wide/Deep data;
- strong DATA, weak SEMANTICS → targeted Deep evidence is more useful than thousands of blind Wide pulls;
- weak DIVERSITY → discover more raid groups before collecting more pulls from the same groups;
- high all components → review/publish rather than enriching indefinitely.

## Important safety principle

A high holdout score alone does not mean the encounter is understood. Trivial recurring observations can validate extremely well. v3.7 therefore requires semantic and signal coverage in addition to statistical stability before publication.

## Recompile workflow

Existing v3.6 Private Blob profiles remain valuable. After deploying v3.7:

1. Open Mechanics.
2. Press `RECOMPILE · 0 WCL`.
3. Existing Wide/Deep profile blobs are read from Private Blob.
4. Aggregate is rebuilt using source-isolated train/holdout.
5. Discovery + compiler v3.7 run without WCL API calls.
6. Inspect `/api/wcl/corpus?encounter=<id>&action=model`.
7. Enrich only according to the returned bottleneck/recommendation.

Old Deep profiles do not contain the new enemy buff/debuff streams. Therefore a zero-WCL recompile can discover state families from existing evidence, but some relation-based mechanics may need targeted new Deep enrichment before they become resolvable.
