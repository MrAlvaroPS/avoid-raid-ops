# AvoiD Raid Operations v3.9 — Panel & Data Platform Refactor

Status: **feature branch only** (`refactor/v3.9-panel-data-platform`). Do not merge to `main` until explicit review.

## 1. View ownership and card rhythm

- Every runtime-created top-level card has a page owner.
- Encounter Corpus is owned by **Mechanics**. A connected DOM node is not proof that its page is active.
- `corpus-ui-stability-v1.1.0` preserves the enhanced corpus DOM only while Mechanics is active and hides/delegates everywhere else.
- Shared top-level card spacing is `--raidops-card-gap: 12px`, matching the Golden layouts/stats/page-banner rhythm.
- Nested `encounter-intelligence-v375` contributes no extra outer margin.

## 2. Loading, error and activity contract

There are two layers:

1. `wcl-bootstrap-v389` bounds browser waits for report/status/telemetry/history/intelligence/corpus/report-catalog/knowledge.
2. `data-hub-v390` exposes a compact activity indicator and a 24-entry in-memory activity ring. Only state transitions are logged; polling success is deliberately terse.

The source React client now exposes typed `RaidOpsApiError`, timeout, one bounded GET retry, per-service load/error state and partial-data behavior. Report is the blocking source. Supplemental service failure must not blank valid report data.

## 3. Stored-data mode

`data-hub-v390` wraps the bounded bootstrap fetch layer before WCL consumers load.

- Successful same-origin GET payloads for report/status/telemetry/history/intelligence/**corpus**/report-catalog/knowledge/Iris-capabilities are persisted in browser Cache Storage (`avoid-raidops-v390`).
- `USE STORED` resolves those GET requests from Cache Storage without contacting the external/data services, including the read-only Encounter Corpus view.
- Corpus POST actions remain connected-only; offline mode must never pretend a write/action occurred.
- In connected mode, a network/timeout failure may fall back to the last stored response and records that transition visibly.
- Raw/cache facts are not relabelled as fresh; activity explicitly says when stored fallback is used.

This is a browser operational cache, not the long-term canonical raid database.

## 4. AvoiD report catalogue and selector

Endpoint: `GET /api/wcl/reports`.

Inputs: selected report, guild, bounded lookback days (2–365), optional force refresh.

The **current raid scope is independent from the selected report**. The canonical zone comes from `WCL_CURRENT_RAID_ZONE_ID` when configured; otherwise the deployment/default current report resolves the WCL `zone.id`. The selected report may change what report-scoped screens display, but it cannot redefine what counts as the current raid. Guild reports are queried and retained only for that exact zone ID. Therefore:

- current raid reports are eligible;
- Mythic+ is structurally excluded;
- unrelated/old raids are structurally excluded;
- selecting an old/unrelated report cannot contaminate the current-raid catalogue;
- report-title heuristics are forbidden.

The Data & Logs drawer provides:

- Sync latest (21 days),
- Load history (180 days),
- report selector,
- selected report navigation,
- current mode and latest-log metadata.

Selecting a valid report changes the report-scoped context via the URL. The existing History endpoint remains encounter-wide and re-clusters valid same-zone reports, so selecting one report does not erase its historical context.

## 5. Live log mode

Data Hub live watcher polls the selected report's compact status every 30 seconds.

Controls: START / PAUSE / STOP.

It does not fetch full telemetry every 30 seconds. A compact fingerprint uses pull count/latest fight identity/end time/in-progress state, and a rich refresh is requested only when that fingerprint changes and the pull is closed. The current-raid catalogue refreshes at a slower two-minute cadence. This is intentionally WCL-budget-aware.

## 6. Versioned game knowledge

Model: `game-knowledge-v1`.

Entity types: encounter, phase, boss ability, player ability, aura, talent, state, NPC.

Current bundled seed normalizes existing encounter rule packs into stable entities and attaches Wowhead spell references where an exact spell ID exists. Provider contract:

- WCL observed data: canonical combat identifiers/evidence.
- Raid Ops rule packs: semantic seed.
- Wowhead: reference links/tooltips/enrichment; never silently promoted to canonical combat truth.
- Blizzard Game Data: planned authoritative versioned metadata provider.

Every snapshot has a revision:

`retail:<season>:<patch>:<build>:<content hash>`

`GET /api/knowledge` returns active/candidate revision state.

`POST /api/knowledge { action: "refresh" }` stages a candidate revision.

`POST /api/knowledge { action: "activate" }` makes it active for Iris and records:

- raw WCL evidence remains immutable;
- derived products are invalidated and must be re-derived/reindexed using the new revision.

The active browser runtime already invalidates stored derived report/status/telemetry/history/intelligence snapshots after activation and refreshes the current screen in connected mode. A pending invalidation survives if activation occurs while stored/offline mode is active.

If `IRIS_DATA_DIR` is configured, knowledge revisions persist to local filesystem. Without it, the refactor API uses process memory and reports that honestly. This is intentional preparation for the local persistent data host rather than pretending serverless ephemeral disk is durable.

A durable SQL contract now exists at `server/storage/schema/001_game_knowledge.sql` for revisioned knowledge entities/references and the knowledge revision attached to derived snapshots. The concrete local database adapter is still a separate implementation step.

## 7. Remaining knowledge ingestion work

The model/store/activation contract exists. Population must expand provider-by-provider instead of scraping opaque HTML into canonical state. Next provider work:

- WCL observed ability/aura/talent identifiers from canonical report/corpus evidence;
- Blizzard patch/build/season metadata and supported Game Data resources;
- optional Wowhead reference enrichment around already-known IDs;
- player spell/talent/spec catalogue;
- durable reindex worker for all database-backed derived report/history/intelligence snapshots after activation.

The current branch does **not** claim that the complete retail ability/talent universe has already been ingested.

## 8. Iris operations-management contract

The v3.9 controls are not UI-only features. They are explicit Iris platform capabilities.

Human-readable contract:

`IRIS-OPERATIONS.md`

Machine-readable source of truth:

`server/iris/capability-contract-v390.mjs`

Runtime discovery endpoint:

`GET /api/iris/capabilities`

Browser operations bridge:

`window.__AVOID_IRIS_OPERATIONS__`

The existing Iris runtime advertises the contract/endpoint/bridge through `window.__AVOID_IRIS__`, so a future Iris assistant or agent surface can discover and call the same bounded operations instead of duplicating DOM button behavior.

The bridge currently exposes:

- recent activity inspection;
- connected/stored mode control;
- current-raid catalogue inspection;
- Sync latest;
- Load history;
- report selection;
- live start/pause/stop/tick;
- game-knowledge status;
- knowledge candidate staging;
- knowledge activation.

The machine contract also tells Iris which actions are `automatic`, `bounded`, `operatorRequested`, `explicitApproval`, or not yet available. In particular:

- selecting report/data/live context is operator-requested;
- activating a knowledge revision requires explicit approval because it invalidates derived interpretations;
- expensive corpus mutation/full maintenance remains approval/resource gated;
- planned durable reindex/provider work must never be presented as already executable.

This capability layer is intentionally versioned so Iris can evolve without silently gaining permissions or pretending a partial provider is complete.

- inside the normal `build` command;
- before `npm version`;
